# Todo 任务命令

命令由内置 `pi-deck-todo` 扩展提供，只约束本次任务，不是跨会话持续模式。

| 命令 | 行为 |
| --- | --- |
| `/todo [任务正文]` | 提示 Agent 先建立、再维护清单；允许提问，不自动续跑。 |
| `/todo-goal [任务正文]` | 首次成功添加待办之前允许澄清；之后程序级阻断 `ask_question`，任务未完成时尝试续跑。计划模式启用期间拒绝启动（提示先 `/plan off`），保留现有清单。 |
| `/todo-resume [用户补充]` | 恢复当前会话中已暂停的 goal（阻塞、连续错误或安全边界不支持），保留原清单；补充文字会作为可见的只读“补充”轮次交给 Agent。 |

没有正文时读取当前分支最近的用户任务，包括此前通过这两条命令明确指定的任务；没有可用任务时先显示输入框澄清。Agent 正在运行时，不用命令替换正在执行的任务，需先等待或停止。

`/plan-progress` 仍然只查看计划进度。`/todo` 不再提供查看、折叠或展开列表的旧功能；列表从会话标题处的 todo widget 查看。命令不会隐式解除计划模式及其只读限制。计划模式启用期间 `/todo-goal` 与 `/todo-resume` 都不会启动新一轮（只读模式下 goal 无法推进，只会空转），没有挂起的 goal 时，`/todo` 仍可用于只读探索；已有 goal 被计划模式接管时，`/todo` 会拒绝替换它并保留原清单。在计划确认框选择“先不执行”“继续规划”或关闭确认框，也会暂停 goal 的自动续跑。

## Goal 的恢复边界

- 自动续跑只依赖 Pi 的 `agent_before_settle` 安全收尾事件，通过返回上下文与续跑请求交给 Pi 调度。不会在桌面侧重发任务，也不会直接在 `agent_end` 上抢跑。
- Pi 的内建重试、压缩和已排队消息优先。续跑只写入简短指令；Agent 可以通过只读工具 `todo_goal_context` 随时获取原始目标和当前清单。续跑不清空清单，不要求重复已完成操作。
- 空清单不算完成。只有建立过清单、仍有条目且全部完成，才停止 goal 控制；清空清单不会解除提问锁定，同一 goal 内重新建表时 ID 继续递增，避免与先前条目混淆。用户明确要求清空清单后，已完成步骤会记录在 goal 上：后续指令、续跑提示和 `todo_goal_context` 都要求只重建剩余工作并列出“不得重复”的已完成步骤，而不是从头开始。
- Agent 正常结束回复时，只要清单尚未完成，就请求继续执行；不根据工具调用、已完成条目或正常回复的次数暂停。连续三次运行错误仍会暂停，正常结束的轮次会重置错误计数。
- 只有确实无法在现有授权内继续、需要用户介入时，Agent 才应调用 `todo_goal_blocked` 报告原因并暂停；待办未完成或任务困难本身不是阻塞。暂停期间只允许调用 `todo_goal_context`，其他工具被阻断。
- 恢复路径按暂停原因区分：阻塞暂停以及已退出计划模式的暂停可用 `/todo-resume [用户补充]`，也可直接回复普通消息（视为恢复指引，不替换任务）；连续三次错误暂停和安全边界不支持导致的暂停只能用 `/todo-resume` 显式恢复，普通回复仍按新任务处理。两种恢复都保留原 goal 和清单；已建立清单的 goal 恢复后注入“继续现有清单”，不会要求重建清单。
- 恢复请求发出后，goal 保持暂停状态直到 Pi 真正开始新一轮（`before_agent_start` 确认）。`pi.sendMessage` 是即发即忘的接口，异步发送失败只会由 Pi 作为扩展错误上报，扩展无法在同一次调用里回滚；因此失败时保持暂停、可重试，而不是假装已恢复。
- 计划模式暂停优先：它只标记暂停并保留原暂停原因（阻塞、连续错误或安全边界不支持），不会清掉用户可读的阻塞信息；此时 `/todo-resume` 不会抢走计划模式的轮次。进入计划模式（`/plan`、输入框计划模式标记）会主动暂停 goal，避免 goal 在只读计划轮次里被意外恢复；任何退出计划模式（`/plan off`、批准计划开始执行、关闭计划确认框，或发送会退出计划模式的普通消息）都会释放计划暂停；普通退出本身不会启动 Agent，释放后即可用 `/todo-resume` 或普通回复恢复。批准计划则明确授权恢复原 goal，并由计划扩展排队执行。
- “保留暂停任务”与“允许普通回复恢复”是两件事：任何暂停的 goal 都会在用户输入阶段保住清单，避免扩展处理顺序不同时被清空；但只有阻塞暂停（以及进入计划模式前可普通恢复的暂停）允许普通回复直接恢复，连续错误和安全边界不支持仍必须 `/todo-resume`，普通回复按新任务处理并在 `before_agent_start` 清空旧清单。
- 计划模式接管期间 goal 处于挂起状态：不注入任务规则、不追加自动续跑，也不清空清单；只允许查看原清单，不允许计划轮次修改它，原 goal 的提问锁不会阻止计划模式澄清；挂起与释放都不依赖扩展加载顺序：计划扩展通过进程内事件发布“计划模式是否接管本轮”，todo 扩展据此在 `before_agent_start` 决定“挂起”“恢复”还是“新任务”，因此即使暂停事件晚到，goal 规则也不会泄漏进只读计划轮次。
- 恢复仅适用于同一会话中仍存活的进程；重启后不能自动恢复 goal。
- 任务通过 Pi 原生可取消入口启动，启动阶段和执行中的主动停止均取消自动恢复。任务替换、会话/分支切换或扩展重载使旧控制失效，旧提示不影响后续任务。
- 只恢复仍存活进程内、到达安全收尾边界的轮次；不处理进程崩溃、应用重启或无法到达该事件的启动失败。恢复历史清单不会自动恢复执行。
- 不提供该事件或不能提供可靠收尾信息的运行时（包括尚未验证的 Rust 版本）不会被强制续跑；命令启动时会说明这一限制。第三方扩展接管 `todo` 工具时，PiDeck 的任务命令不启动控制。

禁止提问不代表获得额外权限。遇到凭据、权限或安全限制时，Agent 应如实说明阻塞原因，不能绕过限制，也不能以无限重试保证完成。

任务原文以可见的 Pi 自定义目标消息保存，桌面实时记录、历史分页和会话摘要均可展示；内部约束和续跑提示仍隐藏。目标在时间线上是独立的只读轮次，使用任务气泡而不是系统诊断卡，不提供用户消息的编辑、删除或重发操作。恢复指引使用同样的只读气泡，标题为“补充”，在实时与会话历史中都可看到；会话标题与摘要仍取原始目标。会话引用（`readMessages`）与 HTML 导出使用同一可见性口径：只包含目标与恢复指引，隐藏的任务规则和续跑提示不会进入引用或导出文件。

任务气泡在桌面投影里是 `system` 只读卡片，但语义上是独立轮次。实时缓存和会话文件索引都用 `turnBoundary` 标记它，轮次分页、显示窗口和“缓存消息 → 文件条目”的编辑/删除定位必须按同一口径计数，否则任务气泡会让后续 user/assistant 条目整体错位。任务消息由扩展写入 `details.messageId` 作为逐条身份，实时事件与历史投影都读取同一个身份去重：同一消息的重放只显示一次，两次内容相同的真实恢复各占一个轮次；只有缺少身份的历史遗留卡片才回退到“正文 + 时间戳”匹配。
